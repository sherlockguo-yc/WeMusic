# 部署下载无限重试问题：根因分析与修复

> 创建日期：2026-07-29
> 状态：✅ 已修复并部署到生产

## 一、背景

WeMusic 采用 GitHub Actions 构建 + N150 deploy-agent 自动部署架构：

```
git push → CI 构建 tar.gz → 发布 GitHub Release
  → webhook 通知 N150 → deploy-agent cron 下载 → rsync 部署 → 重启
```

`deploy-agent.sh` 的下载策略是 **ghproxy.net 镜像优先（预算 360s）→ GitHub 直连兜底（预算 900s）**，单轮最大下载窗口约 21 分钟。下载失败后 cron 下一分钟重新触发。

## 二、问题现象

2026-07-29 凌晨，`636fb8a` 版本持续超过 1.5 小时无法部署成功：

- deploy-agent 日志显示下载 process 重复运行 26~36 次，每次最后都在"镜像超时（360s 预算耗尽）→ 直连也超时（900s 预算耗尽）"后宣告失败
- 错误类型全部是 `下载超时`，单次 curl 90s 超时内下载速度仅 3.5KB/s ~ 23KB/s（完整 tar.gz 约 12.8MB，需 10~60 分钟）
- 之前版本 `3cac812`（约 3 小时前）能正常部署成功，说明问题有突发性

## 三、根因分析

### 3.1 直接根因（网络层）：N150 走的是未经加速的国际出口

通过 DNS 解析对比发现：

| 设备 | DNS 解析 `github.com` | 下载速度 |
|------|----------------------|----------|
| Mac（用户本地）| `100.12.0.32`（路由器 DNS 加速劫持）| 2~3 MB/s，5 秒完成 12.8MB |
| N150 服务器 | `20.205.243.166`（GitHub 官方真实 IP）| 15~35 KB/s，偶尔连通 |

**反事实验证**：让 N150 强制用 Mac 解析到的加速 IP `100.12.0.32` 直连 → 8 秒 timeout（完全不可达），证明该 IP 是一个**绑定在 Mac 当前网关上的私有透明代理加速节点**，不是公开 CDN 端点。

Mac 和 N150 共享同一公网出口 IP（`120.229.47.17`），但实际走的网络路径不同：
- Mac 出口网关 `10.221.86.87`，该路由器对 GitHub 域名做了 DNS 加速劫持 + 透明代理
- N150 出口网关 `192.168.31.1`，没有此加速能力，直接暴露在国际出口的 SNI 层限速下

**结论**：不是 N150 的 IP 被 GitHub/ghproxy"针对封杀"，而是 N150 走的网络路径缺少加速层，真实 GitHub IP 的国际出口受 ISP/GFW 层的传输限速（连接能建立，但数据传输被压到 15~35KB/s）。ghproxy.net 镜像服务商同日也出现了严重性能退化（232B/s ~ 3.5KB/s），进一步恶化。

### 3.2 并发根因（代码层）：断点续传进度被每次失败清零

`download_artifact()` 函数的旧逻辑：

```bash
download_artifact() {
  DOWNLOAD_ERROR="下载失败"
  rm -f "$tmp"                           # ← 每次进入都清空断点续传进度
  if try_download_resumable ... 镜像 ...; then return 0; fi
  if try_download_resumable ... 直连 ...; then return 0; fi
  return 1
}
```

`deploy_job()` 在下载失败后也显式 `rm -f "$tmp"`。

curl 已正确配置 `-C -`（断点续传），且同一次 `try_download_resumable` 内部确实保留了进度。但**跨 cron 任务重试时**（一次 21 分钟预算耗尽 → finish_job 失败 → 下一分钟 cron 重新入队），`download_artifact` 开头的 `rm -f "$tmp"` 会把上一轮辛苦攒下来的部分下载**全部丢弃**，下一轮又从 byte 0 开始。

在 N150 实际 15~35KB/s 的弱网下，12.8MB 约需 10~15 分钟预算，而单轮 21 分钟的预算分配是镜像 6 分钟 + 直连 15 分钟。但 15~35KB/s 是"连接成功后"的速度，实际因为 `connect-timeout 15s` 导致的连接失败浪费了大量预算，有效传输窗口远不足 15 分钟 → **每次都在还差一点就能下完的时候被清零** → 形成无限重试循环。

## 四、解决方案

### 4.1 实施的修复（代码层）

修改 `scripts/deploy-agent.sh` 的 `download_artifact()` 和 `deploy_job()`：

1. **保留跨任务断点续传进度**（核心修复）
   - 新增 `version_marker` 文件（`${tmp}.version`），记录当前断点续传对应的版本号
   - 进入 `download_artifact` 时检查：如果 marker 匹配则保留已有 `$tmp`，版本不同才清空
   - 下载失败时**不再删除 `$tmp`**，让下一轮 cron 任务从已有字节继续
   - 下载成功（`gzip -t` 通过）才清 marker

2. **安全阀：损坏文件检测**
   - 如果本地文件大小已达到远端 `content-length` 但校验仍失败，判定为文件损坏（非未下载完），清空后重新下载，避免陷入"损坏文件永远续传出不来正确结果"的死循环

3. **并发修复：`set -e` / `pipefail` 防护**
   - 安全阀中新增的 `curl | grep | awk` 管道在外网故障时会因 `pipefail` 导致 `set -e` 杀死整个脚本（比原 bug 更严重）
   - 加 `|| true` 和 `${local_size:-0}` 默认值兜底，已用隔离测试脚本反事实验证修复前后行为差异

### 4.2 已验证

| 验证项 | 方法 | 结果 |
|--------|------|------|
| 修复后不会因 `set -e` 崩溃 | 隔离脚本模拟 curl 失败 → 脚本正常跑完 | ✅ |
| 断点续传进度跨任务保留 | N150 真实环境：第一轮故意预算不足制造失败，第二轮启动，文件大小从 889KB 继续增长到 2.1MB | ✅ 单调递增，未清零 |
| 同版本续传 / 不同版本清空 | marker 对比逻辑 | ✅ |
| 完整生产脚本语法 | `bash -n` | ✅ |

### 4.3 已知限制

- **不解决 N150 网络本身慢的根本问题**：此修复只是让"弱网 + 蚂蚁搬家"模式在多次 cron 周期后能成功，不改变单次下载速度
- **环境变量依赖**：安全阀依赖 `$LOG_BASE`（已定义在脚本顶部，设为 `/tmp`）
- **ghproxy.net 服务商不稳定性**：此次事件中该服务商性能严重退化（232B/s），镜像路径当前几乎无法使用，实际全靠直连慢速下载

## 五、后续建议

| 优先级 | 建议 | 说明 |
|--------|------|------|
| 高 | 检查 `192.168.31.1`（N150 路由器）是否支持开启 GitHub/游戏加速功能 | 从根本上解决下载速度问题 |
| 中 | 调研可替代 ghproxy.net 的公共镜像服务 | ghproxy 服务商稳定性不可控 |
| 低 | 考虑改动 CI，将构建产物同时上传到走 Cloudflare 的 CDN（如 R2），N150 从自有 CDN 下载 | 完全绕过 GitHub 域名限制 |
