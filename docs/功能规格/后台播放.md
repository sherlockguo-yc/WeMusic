# 播放架构（单一音频源）

> 描述 WeMusic 播放架构、状态流转、已知问题及修复历史。
> 修改 `src/player.js` 中播放相关代码前**必须阅读本文档**。
>
> **2026-07-13 架构重写**：原「前台 iframe / 后台 bgAudio 双引擎切换」架构已废弃，
> 改为「bgAudio 单一音频源 + 展开视频才切 iframe」架构。原因、方案对比见
> `docs/功能规格/播放架构改造-单一音频源.md`。

## 一、架构概览

WeMusic 只有一个真正会发声的「音频源」：`bgAudio`（一个隐藏的 `<audio id="audio">` 元素）。
无论用户在浏览器前台还是后台/锁屏，日常听歌全部由 `bgAudio` 播放，因此**不存在**「前后台切换音频引擎」这件事，也不需要交叉过渡、健康检查、双引擎并存等复杂逻辑。

唯一的例外：用户主动点击底部播放器的「展开」按钮，想看视频画面时，才切换为 B 站官方 `<iframe>`（画面+声音一起播）。点击「收起」/关闭视频面板后，立即销毁 iframe，改回 `bgAudio` 从记录的进度继续播放声音。

| 状态（`mode` 变量） | 载体 | 说明 |
|------|------|------|
| `'bg'`（默认，唯一常规状态） | `bgAudio` | 无论前台/后台，唯一的声音来源 |
| `'iframe'`（仅展开视频时） | B 站 `<iframe>` | 画面 + 声音一起由 iframe 输出；`bgAudio` 静默预载但不播放 |

切换入口：`expandVideo()` / `collapseVideo()`（由 `videoBtn`/`vpHide` 按钮触发），**不再监听 `visibilitychange` 做音频引擎切换**。`visibilitychange` 仅保留一个用途：用户展开视频后把标签页切到后台时，自动触发 `collapseVideo()`（因为 iframe 会被浏览器限流/静音，必须交还给 bgAudio 才能保证后台仍有声音）。

## 二、音频直链：直连优先，代理兜底

为减少自建服务器带宽消耗（服务器不再代理转发每一次播放的完整音频流量），播放地址解析分两层：

```
GET /api/play/direct-url?bvid=xxx
  → 服务端内部仍走 getAudioStream()（WBI 签名 + 风控规避）解析出 B 站 CDN 真实直链
  → 直接把直链 { url, backup, cid, mime, expiresAt } 返回给前端
  → 前端 bgAudio.src = url（crossorigin="anonymous"，直接跨域播放，不经过自建服务器）
```

**实测结论**（2026-07-13）：B 站 CDN 音频直链本身带 `access-control-allow-origin: *`，用真实浏览器 UA 请求即可跨域播放成功，且能被 `AudioContext.createMediaElementSource()` + `GainNode` 正常处理（不会被标记为 tainted）。但不同网络环境可能分配到不同 CDN 厂商节点，风控策略可能不完全一致，因此保留兜底：

```
_getPlayableUrl(bvid) 决策树（2026-11-04 起为「纯解析」，无副作用，只返回结果）：
  1. 离线（!navigator.onLine）→ 命中 IndexedDB 返回 { blob }；无缓存返回 null
  2. 在线，且本地 IndexedDB 已缓存 → 返回 { blob }（完全不走网络，隧道丢包/弱网时最可靠）
  3. 在线无缓存 → GET /api/play/direct-url?bvid=xxx
     ├─ 成功 → { url }（CDN 直链，播放 + 调度被动落盘）
     ├─ 稿件不可播（VIDEO_UNAVAILABLE）→ 抛错，由调用方换源
     └─ 其他失败 → { url: /api/play/stream, viaProxy: true }（服务端代理）
        └─ bgAudio error 事件仍有最终兜底：代理也失败 → 再查一次缓存 → 无缓存则走恢复流程
```

**为什么解析阶段不生成 Blob URL、不改全局状态**：`_getPlayableUrl` 是 async，返回时调用方可能已被取消（用户切歌、crossfade 被新一轮覆盖）。若在这里回收共享的 Blob URL，会把新歌正在使用的链接一并作废（2026-11-03 复核时用真实 `<audio>` 复现：新歌接管时 `MEDIA_ERR_SRC_NOT_SUPPORTED`）。因此 URL 的创建与 `_cacheUse` / `_usedFallback` / `_lineHint` 的写入统一放到 `_applyPlayable(info, slot)`，由调用方**校验完 `playSeq` / `_crossfadeSeq` 之后**再调用：

| slot | 持有者 | 变量 |
|------|--------|------|
| `'cur'` | `bgAudio` | `_cacheUrl` |
| `'next'` | crossfade 的 `_nextAudio` | `_nextCacheUrl`（接管成功后所有权转给 `_cacheUrl`） |

> **直连的现实**（2026-11-03 N150 实测）：B 站 `upos-sz-*` 节点对浏览器直连一律 **403**（无 Referer、或 Referer 为本站，均 403；只有 `Referer: https://www.bilibili.com/video/<bvid>` + 桌面 UA 才 200/206），但 `mcdn.bilivideo.cn` 节点可直连成功（206）。浏览器 `<audio>` 带不了这组头，所以不能删掉直连（mcdn 节点可用），只能让它失败得更快（见 5.5 直连探活）。

直链有效期约 114 分钟（`deadline` 查询参数），足够单曲播放，暂停超长时间后继续播放可能过期，届时会触发 error/stalled 走恢复流程重新取一次直链。

### 2.1 直链内存缓存（2026-07-15 新增）

`server/services/bilibili.js` 的 `getAudioStream()` 内部增加了两层内存缓存，避免重复播放/单曲循环/切回上一首时每次都重新请求 B 站：

| 缓存层 | 缓存 key | TTL | 说明 |
|--------|---------|-----|------|
| 直链缓存（`_streamCache`） | `bvid:cid` | deadline - 5min 安全边际 | 命中时跳过 DASH/H5 durl 签名+风控流程 |
| 分 P 缓存（`_pagesCache`） | `bvid` | 1 天 | cid 列表几乎不变，避免每次播放都请求 `view` 接口 |

**实测验证**（curl 分变量测试，2026-07-15）：同一直链可在服务端侧跨请求复用，仅挡了明显爬虫标识的 UA（如 `curl/8.0`）。
> **更正（2026-11-03 N150 实测）**：此前写的"任意 Referer 均可 206"不准确。`upos-sz-*` 节点要求 `Referer: https://www.bilibili.com/video/<bvid>`，无 Referer 或 Referer 为本站均返回 403；该组头只有服务端代理能带，所以浏览器直连这类节点必失败（详见 2 节末尾）。

**缓存失效**：`/api/play/stream` 代理请求失败时，调用 `evictAudioStream(bvid, cid)` 主动清缓存，避免 TTL 内反复返回死链接。

**效果**：同一 bvid 连续两次调用 `getAudioStream`：1534ms → 0ms（命中缓存后瞬时返回）。

### 2.2 本地缓存优先（2026-07-15 新增，2026-11-04 改为在线也优先）

最初只在 `direct-url` 失败后才查缓存；现在**在线时也先查 IndexedDB**，命中即 blob 播放，状态栏显示「本地缓存 · 免流量」（真正离线时显示「离线播放」）。依据：2026-11-03 当日 55 首歌里 33 首被重复播放（共 101 次），这部分不应再受隧道抖动影响。

| 场景 | 本地缓存 | 行为 |
|------|:---:|------|
| 在线 / 离线 | 有 | 直接 blob 播放，不请求 direct-url |
| 在线 | 无 | 直连优先，失败走代理 |
| 离线 | 无 | 无法播放 |

**副作用**：已缓存曲目不再请求 `/api/play/direct-url`、`/api/play/stream`，而服务端只在这两个接口里触发音量归一化分析。为避免「分析失败/缺失的歌永远得不到重试」，`GET /api/play/gain` 现在对**已登录**请求在响应后补触发分析（带 10 分钟冷却，响应字段不变）。

`bgAudio error` 事件中的三级降级（直链→代理→缓存）保留，作为"无缓存歌曲"的安全网。

## 四、播放流程

### 4.1 正常播放一首歌（`playCurrent` → `startVideo`）

```
playCurrent()
  ↓
检查当前歌曲是否被标记为「不喜欢」→ 是 → playNext(true) 跳过
  ↓ 否
bvid 是否已知？
  ├─ 是（缓存命中）→ 跳过 resolve
  └─ 否 → 显示加载态（播放按钮→旋转 spinner，封面→呼吸脉冲遮罩）
         → POST /play/resolve（B 站搜索匹配，约 1~3s）
         → 成功后清理加载态
  ↓
bvid 确认后立即 prefetchNextBvid()  // 预取下一首 bvid，与直链解析并行
  ↓
startVideo(bvid, title, dur)
  ↓
if (mode === 'iframe')
    mountVideoAt(bvid, title, 0)     // 保持展开状态，画面切到新歌
    _loadBgTrack(bvid)                // 静默预载 bgAudio，供随时收起
else
    _loadAndPlayBgTrack(bvid, 0)      // 请求 direct-url（可能命中直链缓存）→ bgAudio.src → play()
  ↓
startTimer(dur) → _restartTick()      // 启动每秒 tick
```

**预取提前**（2026-07-15）：`prefetchNextBvid()` 从 `startVideo()` 末尾移到 `playCurrent()` 中 bvid 确认后立即触发，与 `startVideo` 内的直链解析并行执行，不等直链请求完成再预取。

**加载态感知**（2026-07-15）：当 bvid 缓存未命中、需要进 `/play/resolve` 做 B 站搜索匹配时：
- 播放按钮图标 → 旋转 spinner（Lucide Loader2 + CSS spin 动画）
- 封面区域 → 半透明呼吸脉冲遮罩（`#npCoverWrap.loading::after`）
- resolve 失败/无结果时恢复为 PLAY_ICON + 移除 loading class
- resolve 成功后 `startTimer` 直接覆盖为 PAUSE_ICON，封面同步清掉 loading

### 4.2 展开视频（`expandVideo`，由「展开」按钮触发）

```
用户点击「展开」
  ↓
记录 bgAudio.currentTime 为起播秒数
  ↓
bgAudio.pause()
mode = 'iframe'
  ↓
mountVideoAt(bvid, title, 起播秒数)   // 创建 iframe，从该秒数起播
  ↓
_restartTick()                        // tick 切换为「计时器估算」模式
```

### 4.3 收起视频（`collapseVideo`，由「收起」按钮/关闭视频面板/标签页切后台触发）

```
用户点击「收起」（或标签页切到后台）
  ↓
记录 elapsed（展开期间计时器估算的进度）
  ↓
销毁 iframe
mode = 'bg'
  ↓
_playBgAudioWithRetry(记录的进度)      // bgAudio seek 到该进度 + play()（失败重试 10 次）
  ↓
_restartTick()                        // tick 切回「读取 bgAudio.currentTime」模式
```

### 4.4 自动切歌判定（`autoAdvance` 触发条件）

- `mode === 'bg'`：`bgAudio` 的 `ended` 事件（真实播完）触发。
- `mode === 'iframe'`：计时器估算的 `elapsed >= totalDur + 1` 触发（因为 iframe 跨域无法读取真实进度）。
- 播放失败/卡顿统一进入 `_recoverOrAdvance`（见第五章），**只有在同源重试、换源都用尽后才切歌**。
- `bg` 模式下的**停滞检测**：`_tick()` 中，「已出声」且 `currentTime` 连续 8 次（约 8 秒）不前进 → 进入恢复流程（不再直接切歌）。

## 五、播放容错（针对 `bgAudio`，`mode === 'bg'` 时生效）

> **2026-11-04 重写**。此前每个超时回调各自持有全局 `setTimeout` 句柄，没有"这个回调属于哪次加载"的概念，导致换歌/换线路后旧回调仍会触发、`canplay` 超时后监听被摘除、恢复闸门过早放开等一批时序缺陷。现在统一用**加载代次（gen）**约束：每次换 `src` / 换线路 / 换歌都会 `_beginLoad()`（`_guard.bump()`），所有挂在旧代次上的定时器与监听器被清掉或自动作废。纯逻辑在 `src/playback-guard.js`，有假时钟单测。

### 5.1 加载代次与 `_beginLoad`

- 触发点：`playCurrent`、`_playBgAudioWithRetry`（每次加载的统一入口）、`_loadBgTrack`、`_completeCrossfade`、`destroyVideo`、`_switchToProxy`（暂停时）。
- 作用：清掉具名定时器、执行已登记的清理（摘除 `canplay` / `seeked` 监听）、`_playingSeen = false`、停滞计数清零。
- **顺序约束**：`_armDirectProbe` / `_scheduleCache` 必须在 `_playBgAudioWithRetry` 之后调用，否则会被它自己开启的新代次清掉。

### 5.2 `_playBgAudioWithRetry` 的 `play()` 重试

- 最多 10 次，间隔递增 500ms → 3s；回调内用 `alive()` 校验代次，换歌后自然作废。
- 需要 seek 时等待 `seeked` 再 `play()`（1.5s 兜底）；`readyState < 2` 时等待 `canplay`（`{ once: true }`，换代次时自动摘除）。
- play() 成功后 5 秒健康检查：如果又停了且没被用户暂停，重试（最多 3 次，之后切歌）。
- **加载看门狗**（不论走哪个分支，含「重载并 seek」）：8s 仍未出声且无可播放数据 → 进入恢复流程。**超时不摘除任何监听**——数据哪怕晚到，`canplay` 仍会启动播放；用户暂停时不介入。

### 5.3 `_tick()` 每秒巡检

- `bgAudio.paused`（且已调用过 `play()`）→ 重新 `play()`（意外暂停恢复）。
- 否则用 `evaluateStall`（纯函数）：只对「已出声」的曲目计数，`currentTime` 连续 8 次不前进 → 恢复流程。**不再要求 `readyState >= 2`**——缓冲耗尽时 `readyState` 会掉到 1，恰恰是最需要恢复的场景。

### 5.4 恢复流程 `_recoverOrAdvance({ preferRetry })`

| 触发类型 | 顺序 |
|---------|------|
| `error`（稿件本身坏了） | 换源 → 同源重试一次 → 切歌 |
| 卡顿类（加载看门狗 / 停滞 / `stalled`，`preferRetry: true`） | **同源重试一次** → 换源 → 切歌 |

卡顿类先同源重试，是因为网络卡顿时直接换成另一个视频，用户听到的就不是同一首歌的同一个版本了。

- **恢复闸门 `_recovery`**：同一轮卡顿可能同时触发多个回调，闸门保证只处理一次。选择「延迟重试」时**闸门保持关闭，直到重试真正执行**（1.5s 后）；`playCurrent` 会 `reset()` 取消尚未执行的重试。
- 重试回调执行前校验 `playSeq` 与 `bvid`，从当前进度（`elapsed`）继续，而不是回到 0 秒。
- 换源等待期间用户若已切歌（`seq !== playSeq`），不会替用户再跳一首。

### 5.5 直连探活与 `error` / `stalled` 事件

- **直连探活**：直连 4s 内既无数据也无 `error`（某些节点既不 403 也不给数据，`<audio>` 停在 `readyState=0`）→ 主动 `_switchToProxy`。阈值 4s 而非更短：直连正常时通常很快，但移动网络偶尔会慢，而代理线路首字节实测 1.2~5s，切太早反而更慢。
- `error`：先直连→代理（仅一次，`_switchToProxy` 同时清掉 `_cacheUse`，避免代理播放时仍显示「本地缓存」）；代理也失败则查一次缓存（带代次校验，异步返回时若已换歌则丢弃）；缓存也无则进入恢复流程。
- `stalled`：只在**已出声**后才设 8s 兜底；到点后复核 `readyState < 2` 才进入恢复（缓冲健康时偶发的 `stalled` 不会误伤）。`playing` 事件置位 `_playingSeen` 并清掉 `stalled` / `probe` / `canplay` 定时器。

### 5.6 被动缓存调度

整首音频落盘会再拉一遍（5~12MB）。若与首播并行，在同一条隧道上压两份流量。现在由 `_cacheScheduler` 轮询 `cacheReady`，三条加载路径（常规 / crossfade / 展开视频静默预载）**统一走调度，没有立即下载的旁路**：

| 场景 | 放行条件 |
|------|---------|
| 展开视频（`mode === 'iframe'`） | 立即（声音由 B 站 iframe 直接输出，不占本站隧道） |
| 直连播放 | 已出声且播放满 5 秒 |
| 代理播放 | `readyState ≥ 3` 且缓冲余量 ≥ 30 秒（接近曲尾则只要缓冲到曲尾） |
| crossfade 期间 / 未出声 | 不放行 |

最长等待 120 秒，超时放弃；曲目变化则自动放弃。

### 5.7 测试

- `tests/unit/playback-guard.test.js`：停滞判定、缓存放行条件、代次守卫、恢复闸门、缓存调度（假时钟，含历次缺陷的回归用例）。
- `e2e/playback-resilience.spec.js`：真实 `player.js` + 真实 `<audio>` 的主链路回归（直连无响应 / 403 / 代理首字节很慢 / 重复播放命中缓存）。**该 e2e 在 `5ad056e` 上也能通过，只是端到端保护，不单独证明具体缺陷已修复**；具体时序缺陷由单测覆盖。

## 六、不喜欢歌曲自动跳过（2026-07-13 新增）

用户标记为「不喜欢」（`source_type='song'`，存储在 `blocked_sources` 表）的歌曲会在多处被拦截：
- **`playCurrent()`**：如果当前歌曲被标记为不喜欢 → 调用 `stopPlayback()` + `playNext(true)` 自动跳过
- **`computeNextIndex()`**：计算下一首索引时跳过不喜欢的歌曲（顺序/随机模式均生效）
- **`playPrev()`**：返回上一首时同样跳过不喜欢的歌曲
- **`enqueueNext()`**（手动「下一首播放」）：如果目标是已标记不喜欢的歌曲 → toast 提示并拒绝添加

**死循环保护**：当队列中所有歌曲都被标记为不喜欢时，`computeNextIndex()` 返回 `-1`，`playNext()`/`playPrev()` 会 toast 提示「队列中的歌曲均已标记为不喜欢」并停止播放。

## 七、进度条

`mode === 'bg'` 时，进度条显示的时间 = `bgAudio.currentTime` 的真实播放位置（每秒读取一次），这是**真实进度**，不再需要多路校准逻辑（旧架构里 postMessage 心跳校正、bgSync 定时校准等均已删除，因为进度来源统一且真实）。

`mode === 'iframe'` 时（仅展开视频期间），因 iframe 跨域无法读取真实播放位置，仍沿用「每秒 +1」的计时器估算，并保留 B 站 postMessage 心跳一次性校正（`_onBiliMessage`，修正 iframe 从创建到真正出声之间的延迟）。

**拖拽跳转（2026-07-13 新增）**：`mode === 'bg'` 时 `seekBar`/`lpSeekBar` 可拖动，松手触发 `seekTo(sec)` → 直接设置 `bgAudio.currentTime`（因为 `bgAudio` 是本地元素，可精确 seek）。`mode === 'iframe'` 时 `seekBar` 保持 `disabled`（B 站官方未公开支持 postMessage 精确 seek），切换 mode 时由 `_updateSeekInteractivity()` 同步更新 disabled 状态。同时接入 Media Session 的 `seekto`/`seekbackward`/`seekforward`，支持锁屏/耳机快进快退（仅 `mode === 'bg'` 生效），并通过 `setPositionState()` 让系统进度条与 `elapsed`/`totalDur` 保持同步。

详细的「进度条主语是谁」「音量到底控制什么」说明见 `docs/功能规格/播放进度与音量控制.md`。

## 八、已废弃的旧机制（供历史排查参考）

以下机制在 2026-07-13 重构中已删除，如果在旧代码/日志中看到相关字样，说明是重构前的行为：

- `visibilitychange` 驱动的前后台音频引擎切换（`_bgPreload`/`_bgUnmuteAndPlay`/交叉过渡等）
- `_startBgSync`/`_stopBgSync`：后台每 4 秒用 `bgAudio.currentTime` 校准计时器的定时器（现在 `bg` 模式下进度本身就直接读 `bgAudio.currentTime`，不需要"校准"一个独立计时器）
- 前台 iframe 静音预缓冲 `bgAudio`、切后台交叉过渡等待 iframe canplay 才停 `bgAudio` 的逻辑
- `paneVisible`/`applyPaneVisibility`/`setPaneVisible`：视频面板显示状态改由 `mode` 变量直接决定，不再需要独立的"面板可见性"状态
