# 「我喜欢的 / 我收藏的」双层级歌曲标记

> 状态：待确认
> 日期：2026-08-11
> 关联决策：独立开关（抖音式）+ 播放器双按钮并排 + 列表行双按钮并排

---

## 1. 用户场景（一句话）

用户在听歌时，对一首歌的喜欢程度有区分——「一般喜欢」点红心（我喜欢的），「特别喜欢」点星标（我收藏的），两个都是点一下即可完成，无需经过歌单的创建/选择流程。

## 2. 数据流

### 存储（新建独立表，零迁移）

```
favorites 表（与 likes 完全对称）：
  user_id   INTEGER NOT NULL
  song_mid  TEXT    NOT NULL
  name      TEXT NOT NULL
  singer    TEXT
  album     TEXT
  album_mid TEXT
  duration  INTEGER DEFAULT 0
  fav_at    INTEGER NOT NULL          -- 收藏时间（列表按此倒序）
  PRIMARY KEY (user_id, song_mid)
```

- **不迁移旧数据**：独立开关模式下，旧 `likes` 数据天然就是「喜欢」；`favorites` 表新建为空。零迁移、零风险。
- **不改 likes 表**：现有红心代码（表、API、前端状态）完全不动，降低回归风险。

### API（server/routes/stats.js，与 likes 路由对称）

| 端点 | 方法 | 说明 |
|------|------|------|
| `/stats/favorites` | GET | 查询所有收藏歌曲（`ORDER BY fav_at DESC`） |
| `/stats/favorites/:songMid` | POST | 切换收藏（存在则删除、不存在则插入），返回 `{ faved: true/false }` |
| `/stats/favorites/check` | POST | 批量查询收藏状态（body: `{ mids: [...] }`，返回 `{ faved: {...} }`） |

### 前端状态

- `state.favMids`（`Set`）：与 `state.likedMids` 平行，启动时随 `loadLikedMids` 一并加载（或独立加载函数）。
- 数据流：点击星标 → `toggleFav(song, btn)` → POST API → 更新 `state.favMids` → 更新按钮态 + 侧边栏计数 + 播放器按钮态。

### 空值 / 异常

- 收藏列表为空 → 空态提示「还没有收藏的歌曲」（与 likes 页一致）。
- API 失败 → toast「操作失败：xxx」，状态不本地先行变更（与 toggleLike 现行为一致）。

## 3. 状态机

### 收藏按钮（星标）toggle

```
未收藏 ──点击──> 已收藏（星标 fill=currentColor + 计数 +1）
   ^                          │
   └────────点击──────────────┘（取消收藏，计数 -1）
```

- **与喜欢完全独立**：点星标不影响红心，点红心不影响星标。四种组合（无/仅喜欢/仅收藏/两者都有）均合法。
- **并发**：快速双击按「切换两次」处理（与服务端 toggle 幂等语义一致，与现有 toggleLike 相同模式）。
- **播放中切歌**：`updateNpFavBtn()` 随 `updateNpLikeBtn()` 一起在切歌后调用，星标状态跟随当前歌曲。

### 页面视图（我收藏的页）

复用 likes 页两种模式：`list`（列表）/ `singer`（按歌手分组），tab 切换。

### 推荐算法权重（server/routes/stats.js）

- 现状：红心 +3.0、歌单 +2.5。
- 调整：**收藏 +5.0**（明显高于喜欢），仅喜欢保持 +3.0。收藏的歌曲同时可能也喜欢（独立开关），取最高分即可（当前逻辑 `if (likedMids.has(...)) score += 3.0` 为独立加分，需改为分支判断：收藏 +5、仅喜欢 +3，避免叠加成 +8）。

### 其他引用点检查

- `stats.js` 周报（`/api/stats/summary`）只统计 likes 表 → 不动。
- `migration.js` 导入播放记录涉及 likes？——导入逻辑不动，收藏表不做迁移导入（老数据无收藏概念）。
- 右键菜单（ctxMenu）：可加「收藏」项（可选，非本次必做）。

## 5. 边界与失败

| 场景 | 行为 |
|------|------|
| 歌曲无 `song_mid` | toast「该歌曲无 mid，无法收藏」（与 toggleLike 一致） |
| 收藏列表为空 | 空态提示「还没有收藏的歌曲」 |
| 列表行 ops 区变宽 | **风险**：`.song-row` ops 列现宽 112px、3 按钮（喜欢/不喜欢/更多）；加星标后 4 按钮。需实测挤压情况，必要时调 grid 模板（`28px 1fr 1.2fr 0.8fr 20px 56px 112px` → 调整 ops 列宽） |
| 移动端播放器 `.np-actions` | 3 按钮变 4 按钮，720px 断点下需检查是否换行/挤压 |
| API 网络失败 | toast 失败提示，按钮态不变 |
| 星标 vs 书签图标混淆 | **必须用星标（Lucide Star）**：`.song-row` 标记列已用书签图标表示「已在歌单中」，收藏若用书签会语义冲突 |

## 6. 备选方案对比

| 方案 | 说明 | 结论 |
|------|------|------|
| A. likes 表加 `type` 列 | 单表双类型，需改主键 + 数据迁移 + 改所有现有 SQL | ❌ 改动大、迁移风险，收益低 |
| B. 新建 favorites 独立表（**选定**） | 与 likes 对称，现有代码零改动，API/前端各加一层平行实现 | ✅ 风险最低，代码重复量小（3 端点 + 几个函数） |
| C. 收藏复用歌单（「收藏」= 自动建隐藏歌单） | 复用歌单存储，但歌单有 id/排序/删除语义，与「收藏」语义不匹配，且推荐算法要改歌单类型判断 | ❌ 语义错位，复杂度更高 |
| D. 分级模式（收藏自动含喜欢） | 用户只需记一种操作，但用户已明确选独立开关 | ❌ 用户已否决 |

## 7. 验收标准

1. 播放器播放一首歌，点星标 → 星标变实心，「我收藏的」侧边栏计数 +1；再点 → 恢复空心、计数 -1。
2. 搜索/歌单等歌曲列表的每一行有星标按钮，点一下即收藏，刷新页面后星标状态保持。
3. 侧边栏点「我收藏的」→ 显示收藏歌曲列表（列表 / 按歌手两种视图可切换，与「我喜欢的」页一致）。
4. 收藏与喜欢互不影响：只点红心的歌不出现在「我收藏的」；只点星标的歌不出现在「我喜欢的」；两者都点的歌两边都出现。
5. 推荐页（发现）中：被收藏的歌曲比仅喜欢的歌曲获得更高的推荐分（权重 +5 vs +3）。
6. 老用户的既有「我喜欢的」数据不受影响，无需迁移。
